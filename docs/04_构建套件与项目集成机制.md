# ESPEZUpdater · 构建套件与项目集成机制

- 版本：v1.0
- 日期：2026-10-09
- 配套：`docs\01_设计方案_通用固件升级工具.md`、`docs\02_面向AI的接入与出包指南.md`、`docs\03_固件协议契约.md`
- 读者：工具维护者、接入项目方

本文说明「**构建能力如何从升级工具中独立出来、由项目取用，且构建产物落在项目侧**」的完整机制。

---

## 1. 三层职责划分

| 层 | 位置 | 职责 | 不做什么 |
|---|---|---|---|
| **运行时工具** | `ESPEZUpdater\`（`server.ps1`、`public\`、`esptool.exe`、`flash_cli.bat`、`*.bat`） | 提供本地网页 GUI、Web Serial 烧录、串口配网 | 不包含任何项目专有字段、不参与编译 |
| **构建套件** | `ESPEZUpdater\build-kit\`（`build_common.ps1`、`empty_creds.ps1`、`templates\`） | 通用构建驱动与空凭据保障链；供项目内置后调用 | 不硬编码任何项目；不把产物写回工具仓 |
| **项目侧** | `<项目>\firmware-updater\`（`build-kit\` 副本、`runtime\`、`build.json`、`profile.json`） | 存放项目构建档/UI 档与运行时工具副本；**产出并持有构建产物** | 不修改工具仓 |

**核心原则**：工具仓只维护「通用运行时 + 通用套件」；项目专有内容（`build.json`/`profile.json`）
与构建产物（`firmware\`、zip）一律属于项目。

## 2. 为什么这样分

- **独立**：构建套件不依赖工具仓的具体路径，项目内置后可离线、可独立升级；
- **项目取用**：项目复制套件副本，构建行为完全在项目内，工具升级不影响既有项目构建；
- **产物归属项目**：`firmware\`、`verify.log`、zip 生成在项目目录，便于项目自身版本管理、
  与源码同仓归档、按项目发布；工具仓保持干净，不含任何固件二进制。

## 3. 目录布局

### 3.1 工具仓（ESPEZUpdater）

```
ESPEZUpdater\
├─ server.ps1 / 一键升级.bat / upgrade.bat / flash_cli.bat / esptool.exe
├─ public\                       # 运行时网页工具（通用）
├─ build-kit\                    # ★ 独立构建套件
│  ├─ build_common.ps1
│  ├─ empty_creds.ps1
│  ├─ templates\{build,profile}.example.json
│  └─ README.md
├─ docs\ 01 / 02 / 03 / 04
└─ README.md / .gitignore
```

### 3.2 项目侧（以「桌面时钟」为例）

```
F:\ESPDesktopClock\firmware-updater\
├─ build-kit\                    # ← 复制自工具仓 ESPEZUpdater\build-kit\
├─ runtime\                      # ← 复制自工具仓运行时（server.ps1 / public\ / esptool.exe / flash_cli.bat / *.bat）
├─ build.json                    # 项目构建档
├─ profile.json                  # 项目 UI 档
└─ dist\                         # ★ 构建产物（由 build_common.ps1 生成）
   ├─ firmware\<变体>\{bootloader,partitions,boot_app0,app}.bin + manifest.json + profile.json + VERSION.txt
   ├─ firmware\profile.json      # 页面引导（加载 manifest 前发现变体）
   ├─ firmware\verify.log        # L1/L2/L3 留痕
   └─ 固件包_v<版本>.zip 或 固件升级工具_v<版本>.zip
```

## 4. 取用方式：内置套件副本（vendor）

项目按以下步骤接入（示例见 `build-kit\README.md`）：

1. 复制 `ESPEZUpdater\build-kit\` → `<项目>\firmware-updater\build-kit\`；
2. 复制运行时工具（`server.ps1`/`public\`/`esptool.exe`/`flash_cli.bat`/`*.bat`，以及 `public\esptool-js\bundle.js`）
   → `<项目>\firmware-updater\runtime\`（仅 `-Bundle` 模式需要）；
3. 依模板编写 `<项目>\firmware-updater\build.json` 与 `profile.json`；
4. 在项目内运行构建（见第 5 节）。

> 升级套件：用工具仓 `build-kit\` 覆盖项目内副本即可，**杜绝代码漂移**（对应设计方案阶段③）。

## 5. 构建与产物模式（构建时可选）

统一入口（在项目目录执行）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build-kit\build_common.ps1 -Build .\build.json [-OutDir .\dist] [-Bundle]
```

| 参数 | 作用 |
|---|---|
| `-Build` | **必填**，项目 `build.json`；相对路径按其所在目录解析 |
| `-OutDir` | 产物目录，缺省 `<build.json 目录>\dist`；**所有产物写入此处** |
| `-Bundle` | 产物模式开关（见下） |
| `-SkipZip` / `-KeepTmp` | 调试用 |

**两种产物模式（构建时二选一）**

1. **仅固件产物（缺省）**
   - 产出：`dist\firmware\<变体>\...`、`dist\firmware\verify.log`、`dist\固件包_v<版本>.zip`
   - 适用：把固件包交给既有/自建的升级工具宿主。

2. **自包含分发（`-Bundle`）**
   - 额外把 `runtimeToolDir` 中的运行时工具复制进 `dist\`，产出可直接分发的
     `dist\固件升级工具_v<版本>.zip`；
   - `dist\` 内部为完整工具根（`server.ps1`+`public\`+`firmware\`+`esptool.exe`+`flash_cli.bat`），
     双击 `一键升级.bat` 即可运行，无需工具仓。

`runtimeToolDir`（`-Bundle` 用）：`build.json` 可选字段，相对 `build.json` 解析；
缺省尝试 `<kitDir>\runtime`；找不到且未配置则明确报错。

## 6. 参数与数据流

```
项目 build.json ──► build_common.ps1
   ├─ sketchDir / fqbn / versionMacro / credentialMacros / genericNeedles / allowValues
   ├─ profileSource ──► 拷贝为 firmware\<变体>\profile.json + firmware\profile.json
   ├─ coreDir ──► 取 boot_app0.bin
   ├─ flash / chip / appSlot / appWarn ──► manifest.json 与体积检查
   └─ runtimeToolDir ──►（-Bundle）复制运行时工具到 OutDir
                │
                ▼
        OutDir\firmware\... + verify.log (+ zip)
```

- `profileSource`、`runtimeToolDir` 等相对路径一律相对 **build.json 所在目录**；
- `build_common.ps1` 只读写 `-OutDir` 下的 `build_tmp\` 与 `firmware\`，**不触碰项目源码**。

## 7. 空凭据保障链（fail-closed）

`build_common.ps1` 在**项目副本**上执行，任一层失败即中止、不产出可分发产物：

| 层 | 实现 | 检查 |
|---|---|---|
| L1 | `build-kit\empty_creds.ps1` | 按 `credentialMacros` 清空副本 `config.h`（兼容多行 PEM）并自检 |
| L2 | `build_common.ps1` | 独立断言副本宏全空 + 扫描副本源码 `genericNeedles` / 非白名单内网 IP |
| L3 | `build_common.ps1` | 对四件套做 ASCII + UTF-16LE 字节扫描（工作目录真值反查 + 通用特征 + 内网 IP） |

通过后写 `firmware\verify.log`（含模式、命中 0、allowlist、时间、版本），随包分发。

## 8. 不影响 Arduino IDE

- 构建只写 `-OutDir\build_tmp\` 副本，项目源码（含 `config.h`）零改动；
- `fqbn` 显式声明与 IDE 相同的菜单选项（`CDCOnBoot=cdc`、`FlashMode=dio` 等）；
- 开发者可继续用 Arduino IDE 编译上传；分发包才为空凭据。

## 9. 接入检查清单

- [ ] 已复制 `build-kit\`（及 `-Bundle` 所需的 `runtime\`）到项目侧；
- [ ] `build.json` 的 `sketchDir` 只读、`fqbn` 与 IDE 一致；
- [ ] `credentialMacros` 列全、`genericNeedles`/`allowValues` 已按项目填好；
- [ ] `profile.json` 的 `fields[].key` 与固件协议键一致，可选 `protocol` 映射已按需配置；
- [ ] 运行构建后 `dist\firmware\verify.log` 命中 0 / PASS，`manifest.json` 的 `credentials:"empty"`；
- [ ] zip 不含 `build_tmp`/`elf`/`map`/`sdkconfig`；
- [ ] `-Bundle` 产物 `dist\` 可直接双击 `一键升级.bat` 使用。
